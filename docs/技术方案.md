# ATK 鼠标电量查看工具 · 技术方案

面向 ATK / VXE / VGN 系 2.4G 鼠标的 Windows 电量读取工具。本文说明技术选型依据、模块划分、与两个参考项目的异同、ATK 设备的实现要点，以及实测性能。

文中所有性能数字均在本机（Windows 11 / R5 9500F）实测，测试对象是一只在 `373B:1278` 上枚举出来的 ATK 2.4G 接收器。

---

## 1. 结论速览

| 项目 | 结论 |
|---|---|
| 实现语言 | Rust（GNU 工具链，`rust-lld` 自包含链接） |
| 依赖 | **零第三方 crate**，Win32 全部手写 FFI |
| 产物 | `atk-tray.exe` **323 KB**（托盘 + 面板）· `atk-battery.exe` **297 KB**（CLI），均无运行时、无 DLL |
| 界面 | 原生托盘 + GDI 自绘面板，零 GUI 框架 |
| 冷启动 | 82 ms（首次），热启动扫描 20–31 ms |
| 常驻内存 | CLI 私有提交 **2.1 MB**；托盘版 38 MB（窗口 + Shell 集成），跨刷新周期不增长 |
| 空闲 CPU | 0（定时器驱动，不轮询、不忙等） |
| 协议覆盖 | ATK 家族两套协议：Compx 17 字节 / Nordic 64 字节 |

一句话：**这个场景的瓶颈不是 CPU，而是分发形态。** 下面第 3 节会把这句话讲清楚。

---

## 2. 需求与边界

要解决的问题很窄：鼠标用 2.4G 接收器连着，Windows 不自带电量显示，每次想知道还剩多少电只能开官方驱动。

参考项目给了两条路线：

- `2.4G-battery-viewer`：Python + ctypes，零依赖，硬编码两台设备的协议
- `quiet-battery`：Rust + hidapi + windows-sys，单 EXE，多品牌白名单，完整托盘 UI

本项目只覆盖 ATK 品牌，但要求协议层能容纳 ATK 内部并存的多个协议代际。

**明确的非目标**：不做宏、DPI、灯效、固件升级；不修改设备任何设置；不常驻后台偷偷上报。

## 3. 技术选型

### 3.1 候选对比

| 方案 | 端到端耗时 | 私有内存 | 分发体积 | 运行时依赖 | 判断 |
|---|---|---|---|---|---|
| Python + ctypes | 105 ms | ~10 MB 基线，带 GUI 更高 | PyInstaller 10–15 MB | CPython | 能跑，分发差 |
| Python + hidapi | 同上 + DLL 加载 | 同上 | 同上 + hidapi.dll | CPython + DLL | 更差 |
| **Rust + 手写 Win32** | **62 ms** | **2.1 MB** | **297 KB** | **无** | **选用** |
| Rust + hidapi | 相近 | 相近 | + 静态 hidapi | C 运行时 | 多一层无必要的抽象 |
| C++ / Win32 | 相近 | ~1.5 MB | ~80 KB | MSVC 运行时 | 体积更小，但构建链更重 |
| C# / .NET | 40–60 ms | ~12 MB | 150 KB（框架依赖） | .NET | 可接受，需目标机有运行时 |
| Go | 相近 | ~5 MB | ~2 MB | 无 | 可行，GUI 生态弱 |

### 3.2 关键判断：别把「性能」当成选型理由

先把成本拆开。一次完整读取由三部分组成：

1. **枚举 HID 接口**：本机 27 个接口，逐个 `CreateFile` + `HidD_GetPreparsedData` + `HidP_GetCaps`，约 15 ms
2. **设备往返**：写 17 字节、等回复，约 5–10 ms
3. **排空旧队列**：一次 12 ms 超时读

也就是说，**单次刷新的物理成本在 30 ms 量级，CPU 计算量几乎为零**。Python 慢的部分是解释器启动（约 50 ms），不是读电量本身。

所以：

- 如果目标是「自己机器上能用」→ Python 完全够，参考项目就是纯 ctypes 实现的
- 如果目标是「发给别人双击就用」→ Python 需要打包、需要处理杀软误报、10 MB 起步，Rust 的 297 KB 优势是碾压性的

本项目选 Rust，**理由是可分发性和常驻成本，不是算力**。这个区别值得说清楚，否则很容易变成「为了性能而性能」。

### 3.3 为什么不用 hidapi

`quiet-battery` 用 hidapi 是合理选择——它要同时支持 HID++、Razer、Beken 等多种通道，抽象层能省事。本项目只需要两件事：枚举接口、在一个 vendor 集合上收发定长报文。

自己写只需 18 个 Win32 函数调用，换来：

- 不引入 C 依赖，不需要 `hidapi.dll`
- 能精确控制超时、取消、排空（这些是 hidapi 的薄弱处）
- 能读到报告长度、usage page 等原始描述符信息，这是几何探测的前提

代价是要自己处理 OVERLAPPED 和几个 Win32 坑，见 6.3。

## 4. 模块划分

```

├── crates/
│   ├── atk-core/                 协议与传输，无 UI 依赖
│   │   ├── src/win.rs            Win32 FFI 声明（结构体、常量、入口）
│   │   ├── src/hidapi.rs         hid.dll 四个函数的运行时解析
│   │   ├── src/hid.rs            枚举 Collection + Endpoint 事务
│   │   ├── src/protocol/
│   │   │   ├── mod.rs            按报告几何选择协议家族
│   │   │   ├── compx52.rs        17 字节协议：请求、校验、解析
│   │   │   └── nordic54.rs       64 字节协议：链路索引、状态位、解析
│   │   ├── src/model.rs          型号表（仅用于显示名）
│   │   └── src/lib.rs            Reading / QueryError / scan()
│   ├── atk-cli/
│   │   └── src/main.rs           参数、表格/JSON 渲染、watch 循环
│   └── atk-tray/                 托盘 + 面板，零 GUI 框架
│       ├── src/main.rs           消息循环、单实例、工作线程、托盘与菜单
│       ├── src/winui.rs          User32 / GDI / Shell32 绑定
│       ├── src/paint.rs          面板绘制
│       └── src/icon.rs           电量图标（运行时 GDI 生成）
├── tools/probe_hid.py            独立探针，用于摸新设备的协议
├── docs/技术方案.md
└── .cargo/config.toml            rust-lld + self-contained 链接
```

数据流是一条直线：

```
SetupDiGetClassDevs
      ↓  27 个 HID collection
按 VID 过滤（373B / 3554 / 260D / 33E4）
      ↓
几何匹配：usage page + usage + 输入/输出报告长度
      ↓                    ↘ 不匹配 → 丢弃（不发任何命令）
protocol::detect → Family::Compx52 | Family::Nordic54
      ↓
Endpoint::open（读写权限、OVERLAPPED）
      ↓  排空 → 写请求 → 等回复 → 校验
Reading { percent, millivolts, power }
      ↓
DeviceReading（含 name / link / family / 原始 path）
      ↓
CLI 表格 | JSON | watch
      ↓
面板窗口 + 托盘图标（atk-tray）
```

**分层原则**：协议解析是纯函数（输入字节、输出 `Reading` 或错误），不碰句柄。这样 11 个单元测试可以完全离线跑，包括用真实抓包做的回归。

## 5. 与两个参考项目的异同

| 维度 | 2.4G-battery-viewer | quiet-battery | 本项目 |
|---|---|---|---|
| 语言 | Python 3.10+ | Rust 2024 | Rust 2021 |
| 依赖 | 零（纯 ctypes） | hidapi + windows-sys + windows | **零** |
| 产物 | 需 Python / 打包 | 单 EXE | 单 EXE 297–323 KB |
| 协议识别 | 硬编码 VID:PID | 白名单 profile + 明确 ID | **几何探测**，型号表只给名字 |
| 覆盖范围 | 2 台设备 | 多品牌多型号 | ATK 家族两个协议代际 |
| 传输 | ctypes + 重叠 IO | hidapi（HID++）+ 原生重叠 IO | 原生重叠 IO，全部手写 |
| 界面 | tkinter 面板 + 托盘 | 原生窗口 + 托盘 + 通知 | CLI + 原生托盘 + GDI 自绘面板 |
| 错误处理 | 界面提示 | 严格分层、状态机 | 严格校验 + 明确错误枚举 |
| 许可 | 未声明 | PolyForm 非商业 | 待定 |

### 相同的部分

1. **只用 Input/Output Report，不用 Feature Report**。ATK 的 vendor 集合要么没有 Feature 通道，要么长度对不上。
2. **查询前要排空输入队列**。否则会读到上一次的残留报文。
3. **不能在同一句柄上「阻塞读 + 并发写」**。参考项目记录过这会直接杀进程，本项目全程 OVERLAPPED 串行，规避同一问题。
4. **鼠标休眠时收不到回复**，且与「设备不存在」无法区分——只能提示用户动一下鼠标。

### 关键差异：协议识别方式

这是本项目与两个参考项目最重要的分歧。

两个参考项目都倾向于「VID/PID 白名单」：列出确切的型号 ID，匹配上才发命令。这很安全，但新鼠标上市就要等作者更新。

本项目改成**能力探测**：

```
usage page == 0xFF02 && usage == 0x0002 && in == 17 && out == 17  → Compx 17 字节
usage page == 0xFF05 && in == 64 && out == 64                    → Nordic 64 字节
```

型号表退化成一张「显示名映射表」，匹配不到就显示 `ATK family 373B:XXXX`，功能不受影响。

这个设计不是拍脑袋，是被现场情况逼出来的——见 6.2。

安全边界仍然守住：只在 `usage_page >= 0xFF00` 的 vendor 集合上、只发两种固定的只读查询、只接受能通过校验和的回复。不扫描、不爆破、不试写。

## 6. ATK 实现要点

### 6.1 两套并存的协议

ATK 内部至少有两个协议代际，**不能按品牌或 VID 判断**：

**A. Compx / Nordic 52840 —— 17 字节**

```
请求（17 字节，其余补 0）
08 04 00 00 00 00 00 00 00 00 00 00 00 00 00 00 49

实测回复（373B:1278，电量 65%）
08 04 00 00 00 02 41 00 0F 8D 00 00 00 00 00 00 6A
                  ↑  ↑  ↑^^^^
               65%  标志  3981 mV
```

- 集合：`usage page 0xFF02 / usage 0x0002`，Input = Output = 17
- 校验：17 字节求和 mod 256 == `0x55`
- 电量：byte 6；电源标志：byte 7（0 放电 / 1 充电）；电压：byte 8–9，**大端**
- byte 5 是状态字节（0x02 表示电量有效）

**B. Nordic 54L15 —— 64 字节**

```
请求（64 字节）
08 7D 72 02 00 01 07 01 00 ...

回复
08 72 00 3A 00 07 01 64 16 11 00 ...
                     ↑  ↑^^^^
                  100%  4374 mV
```

- 集合：`usage page 0xFF05`，Input = Output = 64
- byte 2 是状态：`0` = 鼠标本人应答，`1` = 没应答（休眠 / 超距）
- byte 5–6 回显请求，用来拒绝过期回复
- byte 5 是**链路索引**：`0` 走有线，`1` 走接收器。选错要么静默，要么回一个 `status=1` 的旧包
- 电压：byte 8–9，**小端**

**注意两套协议的电压端序相反。** 按小端读 17 字节协议会得到 36 V 这种一眼假的值——这是实测才暴露的问题，文档和参考实现里都不明显。

### 6.2 实测发现：同一 VID 下两个协议

本机插入的设备是 `373B:1278`，它不在任何公开的型号表里。枚举结果：

```
373B:1278  0001:0002    8   0   0
373B:1278  FF05:0000    8   0   0     ← usage page 对，但只有 8 字节输入，不是 64 字节协议
373B:1278  FF03:0000    8   0   0
373B:1278  000C:0001    3   0   0
373B:1278  0001:0080    2   0   0
373B:1278  0001:0006    9   2   0
373B:1278  FF02:0002   17  17   0     ← 命中：Compx 17 字节
373B:1278  FF04:0002    0   0   8
373B:1278  FF06:0002   49  49   0
373B:1278  0001:0002    8   0   0
```

如果按 `usage page 0xFF05` 硬匹配（参考项目对 ATK 的写法），这台设备一个字节都读不出来——它的 FF05 集合是 8 字节的，不是 64 字节。

同一个 `0x373B` 下：

- `1216` → 64 字节 FF05（参考项目记录的旧款）
- `1278` → 17 字节 FF02（本机实测）
- `1155` / `124F` → 64 字节 FF05（ATK Zero，8K 接收器）

**结论：VID 和型号名都不能作为协议判据，只有报告几何可以。**

### 6.3 三个 Win32 坑

**坑 1：`SP_DEVICE_INTERFACE_DETAIL_DATA_W` 的偏移**

这个结构体在 x64 上 `cbSize` 必须是 **8**（整个结构的大小），但设备路径字符串实际从**偏移 4** 开始（`WCHAR` 只需 2 字节对齐）。

按 ctypes/Rust 的自动布局读 `DevicePath` 字段，会从偏移 4 读到正确值——但如果「聪明地」把 `cbSize` 也设成偏移量 8，`SetupDiGetDeviceInterfaceDetailW` 会接受调用却返回错误的名字，后续每个 `CreateFile` 都返回 `ERROR_INVALID_NAME`（123）。

我最初就是这么写的，结果是「枚举到 27 个接口，但一个都打不开」，而且没有任何报错。

**坑 2：系统独占的顶层集合**

鼠标 / 键盘的顶层集合已被系统占用，只能用 `dwDesiredAccess = 0` 打开。能读描述符和属性，但不能发命令。所以流程是两趟：先零权限枚举拿几何信息，命中了再用读写权限重新打开。

**坑 3：不能阻塞读 + 并发写**

参考项目已经记录过：同一 HID 句柄上「阻塞 `ReadFile` + 并发 `WriteFile`」会直接杀进程，连异常栈都没有。本项目所有操作都在 `Endpoint` 内串行、全部用 OVERLAPPED + 事件等待，超时后 `CancelIoEx` 再等 50 ms 收尾。

### 6.4 型号覆盖与扩展

已登记的 ATK 家族 ID（来自 Compx 芯片资料与 `quiet-battery` 的支持矩阵）：

| 型号 | VID | 2.4G | 有线 |
|---|---|---|---|
| ATK F1 Ultimate | 373B | 1031 | 102E |
| ATK A9 Ultimate | 373B | 11D9 | 11B6 |
| VXE MAD R | 373B | 104D | 103F |
| VXE MAD R Major Plus | 373B | 1040 | 104C |
| VXE R1 Pro Max | 3554 | F58A | F58C |
| VXE R1 SE+ | 3554 | F58E | F58F |
| VGN F1 Pro | 3554 | F503 | F502 |
| VGN F2 Pro Max | 3554 | FB3E | FB3D |
| ATK Zero（8K dongle-L1） | 373B | 1155 | 1154 |
| ATK Zero（8K dongle-L0） | 373B | 124F | 1154 |
| **本机实测** | 373B | **1278** | — |

加新设备只有两种情况：

- **同一协议、新 PID**：直接能用，只是名字显示成 `ATK family XXXX:YYYY`。想让它显示型号名，往 `model.rs` 加一行即可。
- **新协议**：先用 `tools/probe_hid.py` 把几何和报文摸出来，再在 `protocol/` 加一个模块，实现 `request()` 和 `parse()` 两个纯函数，然后在 `detect()` 里加一条几何判据。

探针是独立的 Python 脚本，只做枚举和只读查询，不依赖本项目编译产物。

### 6.5 与官方驱动的一致性

同一时刻、同一连接方式下对照官方 ATK HUB 与本工具：

| 来源 | 读数 |
|---|---|
| 官方 HUB 设备卡片 | **60%** |
| 本工具 | **60%**，电芯 3977 mV |

两者一致。说明 byte 6 就是设备自己维护的百分比，不需要额外换算，也不存在「固件值 vs 厂商校准值」的偏差。

## 7. 性能实测

测试环境：Windows 11，AMD R5 9500F，ATK 2.4G 接收器（`373B:1278`）。

| 指标 | 数值 | 测量方式 |
|---|---|---|
| 可执行文件 | 297 KB（304,128 B） | `ls -l` |
| 冷启动扫描 | 82.1 ms | 首次运行 `--timing` |
| 热启动扫描 | 19.6 / 23.1 / 23.6 / 24.0 / 31.2 ms | 连续 5 次 |
| 端到端（含进程创建） | 平均 62 ms，最小 45.6，最大 181.9 | `Measure-Command` × 10 |
| Python 探针对照 | 平均 105 ms，最小 95.2，最大 127.2 | 同机 `Measure-Command` × 5 |
| 私有提交内存 | 2.08 MB | `PrivateMemorySize64` |
| 工作集 | 10.04 MB | `WorkingSet64`（含共享 DLL 页） |
| 线程数 | 4 | 1 主线程 + 运行时 |
| 句柄数 | 142 | |
| 空闲 CPU | 0 | `--watch` 定时器驱动，不轮询 |

几点说明：

- **首次 82 ms 主要花在加载**（镜像页、`setupapi` 初始化），不是代码慢。之后稳定在 20–31 ms。
- **休眠时按超时预算在约 260 ms 内返回错误**（250 ms 读超时 + 队列排空），不是无限等待。设备正常应答在 10 ms 内，250 ms 足够宽松；失败路径不会让界面卡死。
- **工作集 10 MB 看起来不低**，但其中大部分是 `kernel32` / `setupapi` / `hid` 的共享页，这些页系统本来就是热的，不构成真实增量。私有提交 2.1 MB 才是这个进程自己的占用。
- **Python 对照只能说明量级**：105 ms 里约一半是解释器启动，实际读电量的时间两者差不多。这也印证了 3.2 的判断。

托盘常驻的额外成本实测为 **37.98 MB 私有提交**（`t=3s`）→ **38.04 MB**（`t=68s`，跨一个完整刷新周期），基本不增长。大头是窗口与 Shell 集成带来的句柄和线程（562 个句柄、14–16 线程），不是电量读取本身——`atk-core` 单独跑仍然只有 2 MB。

## 8. 已知限制

1. **Windows 11 会把新托盘图标折叠进溢出面板**（任务栏的 `^`），需要用户手动拖到任务栏常驻，程序无法强制其位置。
2. **只验证了一台设备**（`373B:1278`，无线）。有线链路、其他 PID、多设备同时连接都未实测。
3. **厂商驱动并发未验证**。ATK HUB 同时运行时可能抢占 vendor 集合，本项目没有做互斥。
4. **电压只能作参考**。电量是电压估算的，有线时恒压阶段会顶在 100%，拔线后会掉几个点——这是表计特性，不是读了假值。
5. **GNU 目标需要 `rust-lld` 自包含链接**。若改用 MSVC 工具链，删掉 `.cargo/config.toml` 即可，代码无需改动。

## 9. 托盘层实现

`atk-tray` 是不引任何 GUI 框架的原生实现，约 700 行：

```
atk-tray
├── 单实例      CreateMutexW，已存在则直接退出
├── 窗口        RegisterClassW + CreateWindowExW，固定 404x240
├── 绘制        WM_PAINT 里用 GDI 画，无控件、无布局引擎
├── 托盘        Shell_NotifyIconW，图标运行时生成
├── 刷新        工作线程 scan + PostMessage，UI 线程永不阻塞
├── 菜单        CreatePopupMenu + TrackPopupMenu
└── 退出        WM_DESTROY 里 PostQuitMessage(0)
```

几个实际踩到的点，都是「代码看起来对、界面什么都没有」的类型：

- **图标掩码必须显式清零**。`CreateBitmap` 生成的 1bpp 掩码内容未初始化，随机为 1 时整块图标透明。现象是日志显示 `Shell_NotifyIconW` 返回 1、图标句柄有效，但托盘里什么都没有。
- **DIB 要用 bottom-up**。图标位图按 bottom-up 解释，用负高度（top-down）会得到空图标。
- **GDI 不维护 alpha 通道**。32bpp DIB 上画完，alpha 全是 0，必须先铺一个 key 色（洋红），画完再把 key 色像素置 alpha=0、其余置 255。
- **画刷删除前必须 `SelectObject` 恢复**，否则 `DeleteObject` 静默失败，每次重绘泄漏一个句柄。
- **`Shell_NotifyIconW` 返回 TRUE 只代表消息投递成功**，图标是否真的存在要用 `Shell_NotifyIconGetRect` 查它的屏幕矩形——这是定位「图标不显示」最快的手段。

自启动用启动文件夹里的 `.lnk`（`%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\ATK 电量.lnk`），而不是注册表 `Run` 键：任务管理器 →「启动」里能直接看到并禁用，取消勾选就删掉文件。创建 `.lnk` 需要 `IShellLinkW` + `IPersistFile`，手写 COM vtable 调用即可（`SetPath=20`、`SetWorkingDirectory=9`、`SetDescription=7`、`IPersistFile::Save=6`），不需要额外依赖。快捷方式带 `--tray` 参数，程序据此判断为登录启动，只驻留托盘、不弹面板——否则每次开机都会有个窗口糊到脸上。桌面另有一个不带参数的快捷方式。登录启动（`--tray`）永远静默；手动双击是否弹面板由设置文件 `%LOCALAPPDATA%\ATK Battery\settings.ini` 里的 `show_panel` 决定，对应菜单里的「启动时打开面板」。exe 本身不含图标资源，所以两者都用 `SetIconLocation` 指向同目录的 `atk-battery.ico`（由 `tools/make_ico.py` 生成）。菜单每次打开都重新读文件是否存在，**绝不「自动纠正」用户手动删掉的状态**。

面板布局：设备名 / 大号百分比 / 右侧电压与状态 / 圆角进度条 / 更新时间。配色按电量分档（≥60 绿、30–59 琥珀、<30 红、充电蓝），托盘图标与进度条共用同一套颜色。

刷新策略是**工作线程读、消息线程画**：worker 做一次 HID 读取，结果放进 `Mutex`，然后 `PostMessage(WM_APP_DATA)` 通知界面重绘。读取最坏耗时（鼠标休眠）约 260 ms，这个延迟永远落在工作线程上，不会让窗口卡住。

间隔是自适应的：**读到值后等 60 秒，读不到就 5 秒后重试**。固定 60 秒轮询的问题在于，鼠标休眠期间每次都在超时，用户回来动一下鼠标后，最快也要等一整个周期才能看到新值；改成失败快重试后，唤醒到刷新之间最多 5 秒。设备本身没有可靠的"已唤醒"通知可用——`WM_DEVICECHANGE` 只在 USB 插拔时触发，休眠时设备仍然挂在总线上。

托盘图标是**环形电量表**而不是数字。早期版本把百分比画成字形，但 32×32 的字形缩到 16 px 后两位数就糊成一团。环形的填充弧长本身就是电量，不依赖识字，16 px 下依然能分辨大致档位；中心留空，靠近才用 tooltip 给出精确百分比。

## 10. 复现

```bash
# 工具链（GNU 目标，无需 Visual Studio）
rustup-init -y --default-host x86_64-pc-windows-gnu --profile minimal
# .cargo/config.toml 已配置 rust-lld + link-self-contained

cargo test --release      # 11 个测试，含真实抓包回归
cargo build --release     # target/release/atk-battery.exe

./atk-battery.exe            # 读一次
./atk-battery.exe --json     # 机器可读
./atk-battery.exe --watch    # 30 秒刷新
./atk-battery.exe --dump     # 列出所有 HID 集合（排查用）
./atk-tray.exe               # 托盘 + 面板
python tools/probe_hid.py    # 独立探针，摸新设备协议
```
